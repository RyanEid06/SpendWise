# WP33.5 — Final UX, Reliability & Polish Pass

**Status:** Scope defined; implementation not started\
**Baseline:** WP33 complete and merged; initial planning baseline `3423e60`\
**Next gate:** WP34 final certification, only after the WP33.5 gates in this document pass against the final source

> This document defines the final planned UX, reliability, state-continuity, and data-loss-prevention milestone before WP34. It is a plan, not evidence that implementation or acceptance testing has occurred.

## Product priorities and boundaries

SpendWise realistically has around 1–5 users. Prioritize, in order: correctness; prevention of data loss; security; smooth UX; reliable backups; and reasonable performance.

Do not add enterprise/SaaS complexity, huge-scale systems, payment infrastructure, multi-user authorization, session replay, enterprise analytics, or distributed architecture unless the product scope genuinely changes. Earlier-WP foundations are already strong and should not be rebuilt unnecessarily: layered service boundaries; SQLCipher encrypted native database; encrypted private media; Android Keystore-rooted secrets; App Lock; Backup v3 with Argon2id and AES-256-GCM; installation-based backend authentication; P-256 signing identity; short-lived tokens; quotas/rate limits; HTTPS/CORS/request-size protections; relational SQLite schema, foreign keys, indexes and integrity checking; transactional migrations/recovery; AI local fallback; EN/FR/AR and RTL support; browser/native/Android tests; and WP33 privacy-safe diagnostics/observability.

WP34 final certification must wait until WP33.5 implementation, regression, signed candidate testing, physical Honor-phone validation, all discovered fixes, and final revalidation are complete. Any certification run before later source changes is stale and must not be treated as final.

## WP33.5-01 — Branding, startup and authentication UX

### Branding

Use the approved light/dark logo reference as the source for preparing proper Android launcher/adaptive assets during implementation. **Reference source:** [approved SpendWise light/dark logo](assets/spendwise-logo-light-dark-reference.png). The supplied reference is documentation only for this planning task: do not crop, split, regenerate, resize, edit, convert, or implement it as Android assets here.

- Use the approved light version for the Android launcher/external app icon.
- Inside the app, use the light logo in light mode and dark logo in dark mode.
- Make the Home/top-left logo roughly 32–36dp visually; preserve an approximately 48dp touch target if interactive.
- Check that the full rounded-square logo reads clearly at header size. If it is cramped, the in-app mark may use the core wallet/chart mark while the full approved logo remains the launcher mark.
- Create suitable adaptive/launcher assets during implementation; do not simply shrink the reference PNG.

### Locked and loading surface

Remove the pure black transition seen during App Lock authentication/secure startup without exposing financial data before authentication succeeds. Show a minimal, theme-aware locked/loading surface with the approved logo centered: an appropriate light background in light mode and a SpendWise dark background in dark mode. If secure initialization after successful authentication takes noticeable time, retain the logo and show a subtle progress indicator and optionally “Unlocking…”. Do not flash another screen.

Expected sequence: **Locked → Android system authentication → biometric/device credential success → secure initialization/unlock → Home.** Continue using Android system authentication APIs. Support fingerprint; eligible Android system face biometrics only when exposed by the device/framework at the required security level; and device credential fallback (PIN, pattern, password). Do not build camera-based face recognition or request camera permission for authentication. If biometrics are unavailable or another allowed method is selected, supported device credentials must still unlock. Cancel/dismiss returns to a clean locked state with a clear Unlock action, without a broken or repeating prompt.

### Startup timing and acceptance

The observed biometric-success-to-usable delay is approximately 2.5–3 seconds. Use existing WP33 timing/diagnostic infrastructure to locate time across biometric success → Keystore/key access → SQLCipher/storage initialization → repositories/bootstrap → app state loading → first usable Home frame. Do not hide delay with animation. Optimize only measured, legitimate bottlenecks; never weaken cryptography, App Lock, encryption, or startup safety for a small speed gain.

Accept only after verifying: light and dark launch; no financial data before unlock; fingerprint; eligible device credential fallback; no-biometric path; cancellation/retry; background/resume reauthentication; removal of the black transition; and unlock timing recorded through existing diagnostics.

## WP33.5-02 — Home, Statistics and Settings polish

### Home monetary amount wrapping

Keep currency values on one line (including cases that currently split, such as `$165` / `.00`). Preserve the full amount first; let description/category give up space; ellipsize descriptions as needed; compress spacing reasonably; and allow slight amount-font scaling only for extreme values. The price must never wrap. Check `$5.00`, `$165.00`, `$1,250.00`, `$12,999.99`, long descriptions, French, Arabic/RTL, and all currently supported currency/number formats.

### Statistics

- Largest expenses by month defaults to Top 3 for every selected period, numbered `1`, `2`, `3` (remove `#1`, `#2`, `#3`). For periods with more data, offer **Show all** and an appropriate collapse action. Avoid arbitrary Top 3 versus Top 5 rules by range without a strong UX reason.
- Replace the vague gray monthly spending/remaining icon with a calendar-style icon consistent with existing iconography. Respect theme tint and verify contrast in light and dark modes.

### Settings storage/media and media library

The normal Storage & Media Settings summary prioritizes photo count (`0 photos`, `1 photo`, `2 photos`), not MB/KB. Details may show photo count, storage used, and media management information. Correct capitalization, pluralization, number/text alignment, spacing, light/dark presentation, and RTL layout.

Group Media Library items chronologically with date separators similar to History, preferring the associated expense date where appropriate. Keep it simple; do not create an over-engineered photo-management product.

### Technical diagnostics exposure

Remove the WP33 Technical Diagnostics card from ordinary user Settings, including **Inspect report**, **Export technical report**, and **Clear diagnostics** exposure there. Retain all WP33 diagnostics infrastructure, privacy-safe technical recording, timing/error observability, and useful diagnostic/report/export access on serious startup/storage/recovery failure screens where it helps troubleshooting. This is not authorization to remove diagnostics.

### Terms and Privacy agreement UI

Correct checkbox alignment and text baseline, wrapping, spacing, tappable area, and light/dark/RTL layout. Terms of Use and Privacy Policy links must remain independently tappable.

## WP33.5-03 — Backup, restore and media UX

Simplify the existing backup UI without changing Backup v3 cryptography or compatibility. Remove user-facing “Backup V3” terminology. Replace duplicate choices such as “Backup Data” and “Backup Data + Photos” with **Create encrypted backup**, containing an **Include photos** toggle. Keep the format internally identified as Backup v3.

Redesign the cramped password flow with readable **Backup password** and **Confirm password** fields; adequate vertical spacing; visibility controls where appropriate; mismatch validation; understandable strength guidance where already required; readable validation/errors; prominent **Create Backup** and **Cancel** actions; keyboard-safe scrolling; light/dark/RTL layouts; and accessible hit targets.

Do not weaken Argon2id, AES-256-GCM, Backup v3 security, or compatibility with existing valid backups. Normal hierarchy should be:

1. Create encrypted backup
2. Restore backup
3. Export CSV
4. Import data

Retain legacy JSON backup/import only where compatibility currently requires it, placing it in a smaller **Legacy tools** area rather than presenting it as equally recommended. Correct `CVS` to `CSV` and similar typos.

Regression coverage: encrypted data-only and photo-inclusive backups; existing Backup v3 restore; correct password; wrong-password safe failure; photo restore and attachment references; expected offline backup/restore behavior; and unchanged older-format behavior despite UI wording changes.

## WP33.5-04 — Add/Edit Expense, AI and UI state continuity

### Attachment choices and source chooser

Do not offer newly created **Proof / Reference** attachments. Keep creation choices to **Receipt** and **Purchase photo**. Preserve, safely display, and never corrupt existing Proof/Reference records; hide/remove only the new-record option unless architecture requires otherwise. Provide a SpendWise-themed **Take photo** / **Choose photo** chooser matching the green/white language in light/dark/RTL. Keep Android system photo picker and camera interactions when system UX/security is appropriate.

### Keyboard/IME behavior

When the keyboard opens, keep the form scrollable rather than forcing a full-height fixed form behind it. Respect Android IME insets, keep the focused field visible, make important actions reachable, reflow categories cleanly without huge gaps or avoidable isolated rows, and keep Cancel/Save usable or easy to reach. Validate on real Honor devices, not only an emulator.

### Gemini Apply to Expense Draft

Fix the functional **Apply to expense draft** action: AI suggestion → user taps Apply → relevant suggested values populate the current draft → form visibly updates → user may inspect/edit → user manually saves. Never auto-save an AI suggestion. Add focused regression coverage.

### Cross-tab state and Gemini continuity — source review

**Assessment at baseline `3423e60`: partial/inconsistent; implementation work is required in WP33.5-04, with regression coverage retained.**

Observed source evidence: `AppShell` owns `useAiAnalysis` above the tab branches, and Analysis (`AiInsightsScreen`) receives that hook’s result/loading/error state. Its in-flight Analysis request can therefore outlive an ordinary tab switch while the app process remains alive. In contrast, `AppShell` conditionally renders `StatisticsScreen` only when Statistics is selected. Statistics owns its period, expanded-category, AI result/loading/error state locally; its unmount cleanup increments the request ID, so a response is ignored after switching away. Returning also remounts Statistics and resets its local state. Thus this is not consistently implemented, especially for Statistics; it must not be described as already complete. Evidence paths: `src/app/AppShell.tsx`, `src/app/hooks/useAiAnalysis.ts`, and `src/screens/StatisticsScreen.tsx`.

First reuse existing architecture/state-management conventions. Apply a consistent lifecycle to affected screens without rebuilding a working equivalent or introducing unnecessary global singleton state. Tab navigation alone must neither destroy meaningful tab state nor cancel Gemini work; explicit user cancellation may. On return, show the current loading/result/error state. Preserve useful state such as selected period, filters, ranking expansion, generated result, loading/error, practical scroll/navigation position, and form-owned state; do not retain meaningless transient visuals forever.

Do not conflate tab switching with process death. If the process remains alive, the request continues while another tab is visible. After actual process death/crash/reboot, do not claim the in-flight network request resumes at the same execution point; restore safe durable UI state/cached completed results where supported and show a sane retry/recovery state for interrupted work. This requirement is separate from encrypted expense draft recovery.

Add regressions for: Gemini started in Analysis and Statistics, switch away and return; repeated tab switches while processing; success and failure arriving while another tab is visible; no duplicate request on switching; explicit cancel if supported; and no stale result crossing contexts. Include screen recreation where applicable.

### Category update and historical compatibility

Rename **Food** to **Food & Beverage**; keep **Groceries**; do not add a default Drinks category. Food & Beverage means restaurant, café, takeaway, delivery, pizza, coffee/drinks consumed as dining or outside food, and similar restaurant/café spending. Groceries means supermarket/household food shopping and food/drink primarily bought for home.

Existing Food transactions must remain connected via safe migration/aliasing. Validate database migration, history, filters, statistics, category rankings, import/export, backup/restore, AI suggestions, translations, and RTL. Never create two analytically separate categories accidentally.

## WP33.5-05 — Encrypted unsaved expense recovery (mandatory sign-off gate)

Unfinished Add/Edit Expense work must survive interruptions: app switching, calls, backgrounding, Activity recreation, Android process death, crash, phone power loss, reboot, and reopening. Persist meaningful fields where applicable: amount, description, merchant, category, date, note, add/edit mode, relevant attachment draft references/state, and other meaningful form state.

Drafts must use protected encrypted/private storage. Do not store financial draft contents as plaintext JSON in shared preferences, public cache, or plain files, and do not weaken SQLCipher/private media/Keystore protections. Restore naturally when safe and avoid unnecessary prompts; if intent is ambiguous, a clear **Continue / Discard unfinished expense** prompt is acceptable.

Clear drafts after successful Save; intentional Cancel/Discard when appropriate; relevant Clear All Data/reset; and safely handle deletion of the expense being edited. Never clear only because an Activity was destroyed, process was killed, or app went to background.

Manage attachment drafts without orphaning permanent media, deleting media still needed by a recoverable draft, exposing plaintext, or allowing uncontrolled buildup. Define safe cleanup for abandoned draft media.

Required real process-recreation/process-death tests: type amount → background → return; partially complete form → kill process → reopen; attach photo → kill/reopen; recovered draft → Save; recovered draft → Discard; edit existing expense → interrupt → recover. This is one of two non-negotiable final sign-off requirements.

## Recommended implementation order

Fix everything discovered before WP34 certification and rerun relevant regression. Never mark WP37, final sign-off, production-ready, or release-complete while either mandatory gate remains: **(1) encrypted unsaved-form recovery; (2) final real Honor-phone plus Maestro/native validation.** Keep this blocker valid even if future WP numbering changes.
